# 项目规范

> 本文件定义本项目在 **文件、Git、文档** 三方面的统一规范，所有提交均应遵循。
> 版本：v1.0　更新日期：2026-10-05

---

## 〇、总则

1. 一切以「可追溯、可复现、可交付」为目标。
2. 源码与工作文档随代码做版本管理；定稿交付文档（开题报告 / 论文 / 答辩 PPT）以 Word / PPT 形式归档于 `docs/`。
3. **单一事实来源**：同一信息只在一处维护，其他位置以引用方式指向它。

---

## 一、文件策略

### 1.1 仓库与目录结构

采用**单体仓库（Monorepo）**，前后端与文档同属一个 Git 仓库，仓库根目录即项目根目录。

```
.
├── backend/                    后端工程（Spring Boot）
│   └── .gitkeep
├── frontend/                   前端工程（Vue 3）
│   └── .gitkeep
├── sql/                        数据库脚本
│   ├── 01_schema.sql           建表
│   ├── 02_init_data.sql        初始化数据（字典、角色、管理员）
│   └── 03_test_data.sql        测试数据（题库样例）
├── scripts/                    构建 / 运维 / 工具脚本
├── docs/                       全部文档（见第三章）
├── .gitignore
├── .gitattributes
├── .editorconfig
├── CLAUDE.md                   协作约定（面向 AI 助手）
└── README.md
```

### 1.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| Java 类 / 接口 | 大驼峰 | `PaperGenerateService` |
| Java 包 | 全小写，点分层 | `com.xxx.paper.service` |
| Java 方法 / 变量 | 小驼峰 | `generatePaper` |
| Java 常量 | 全大写 + 下划线 | `MAX_POPULATION_SIZE` |
| 数据库表 / 字段 | 蛇形小写 | `paper_question`、`question_id` |
| Vue 组件 / 视图 | 大驼峰 `.vue` | `QuestionList.vue` |
| JS/TS 变量 / 函数 | 小驼峰 | `fetchPapers` |
| 前端目录 | 小写短横线 | `question-bank` |
| SQL 脚本 | `序号_描述.sql` | `01_schema.sql` |
| 文档 | `序号-中文名.md` | `03-需求规格说明书.md` |
| 图片资源 | 小写短横线 | `system-architecture.png` |

### 1.3 存放原则

- 后端源码 → `backend/`；前端源码 → `frontend/`。
- 数据库脚本（建表、初始化、测试数据）→ `sql/`。
- 构建、部署、数据处理等脚本 → `scripts/`。
- 所有文档 → `docs/`，按阶段编号组织。
- 临时文件、实验产物、构建输出、依赖目录 → **不入库**（由 `.gitignore` 拦截）。
- 大体积数据集 / 题库导入模板 → `docs/99-参考/` 或 `sql/`，并说明来源。

## 二、Git 策略

### 2.1 平台与远程

- 托管平台：**GitHub**
- 远程名：`origin`
- 仓库地址：`https://github.com/esneighbour9/Intelligent-Test-Paper-Generation-and-Analysis.git`

### 2.2 分支模型（轻量模型）

| 分支 | 用途 | 说明 |
|---|---|---|
| `main` | 稳定 / 可交付 | 仅在阶段里程碑合并，并打 Tag |
| `dev` | 日常集成 | 功能开发完成后合入此分支 |
| `feature/<模块>` | 功能开发 | 从 `dev` 切出，完成后合回 `dev` |
| `docs/<主题>` | 文档编写（可选） | 大块文档工作可单独分支 |
| `hotfix/<问题>` | 紧急修复（可选） | 从 `main` 切出，修复后合回 `main` 与 `dev` |

```
main  ──●────────────────────●──────────────●──►
         \                  /              /
          ●───●───●───●───●  dev        ──●
                 \      /
              feature/ga-paper
```

### 2.3 工作流

1. 从 `dev` 切出功能分支：`git switch -c feature/question-bank dev`
2. 在该分支上小步提交（每次提交保持可编译、原子化）
3. 首次推送并关联远程：`git push -u origin feature/question-bank`
4. 功能完成后合回 `dev`：`git switch dev && git merge --no-ff feature/question-bank`
5. 阶段稳定后合入 `main` 并打 Tag

### 2.4 提交信息规范（Conventional Commits）

格式：`<type>(<scope>): <中文描述>`

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改外部行为） |
| `test` | 测试相关 |
| `chore` | 构建 / 配置 / 杂项 |
| `style` | 格式调整（不影响逻辑） |
| `perf` | 性能优化 |

`scope` 为模块名（组卷 / 题库 / 分析 / 前端 / 文档 / 后端 …）。示例：

- `feat(组卷): 实现遗传算法适应度函数`
- `fix(题库): 修复批量导入时知识点丢失`
- `docs(设计): 补充数据库 ER 图`
- `refactor(分析): 抽取 CTT 指标计算工具类`
- `chore: 初始化项目脚手架`

规则：一次提交只做一件事；描述用动词开头、简明扼要；**不得将无法编译的代码提交到 `dev` / `main`**。

### 2.5 标签（Tag）

里程碑打附注标签：`git tag -a v0.1-开题 -m "开题材料完成" && git push origin v0.1-开题`

建议里程碑：`v0.1-开题` → `v0.3-设计完成` → `v0.5-组卷算法` → `v0.7-后端完成` → `v0.9-前后端联调` → `v1.0-系统完成`。

### 2.6 忽略与敏感信息

- `.gitignore` 已覆盖 Java/Maven、Node/Vue、IDE、操作系统、日志、临时文件。
- **数据库密码等敏感配置**写入 `application-local.yml`（已被忽略），仓库只保留 `application-local.yml.example` 模板。
- 严禁提交 `.env`、密钥、证书、生产环境配置。

### 2.7 提交前检查清单

- [ ] 代码可编译 / 可运行，无明显报错
- [ ] 未包含调试代码、临时文件、无关改动
- [ ] 提交信息符合 2.4 规范

## 三、文档策略

### 3.1 格式原则

- **工作文档（Markdown）**：需求、设计、接口、测试、算法说明等 —— 随代码版本管理，便于 diff 与协作。
- **定稿交付文档（Word / PPT）**：开题报告、毕业论文、答辩 PPT —— 归档于 `docs/`。
- 同一文档若同时存在 Markdown 草稿与 Word 定稿，**以 Word 定稿为准**。

### 3.2 文档目录与对应阶段

| 目录 | 内容 | 格式 | 对应阶段 |
|---|---|---|---|
| `00-规范` | 项目规范（本文件） | Markdown | 全程 |
| `01-规划` | 项目整体规划 | Markdown | 全程 |
| `02-开题` | 开题报告 | Word | 开题 |
| `03-需求` | 需求规格说明书、用例与角色 | Markdown | 需求分析 |
| `04-设计` | 系统设计、数据库设计、详细设计、算法设计 | Markdown | 系统设计 |
| `05-接口` | 接口设计文档 | Markdown | 系统设计 |
| `06-测试` | 测试用例、测试报告 | Markdown | 测试 |
| `07-论文` | 论文草稿(MD)/定稿(Word)、`images/` | Markdown + Word | 论文撰写 |
| `08-答辩` | 答辩 PPT、讲稿 | PPT | 答辩 |
| `99-参考` | 文献、参考资料、模板 | 混合 | 全程 |

### 3.3 命名与维护

- 命名：`序号-中文名.md`，如 `03-需求规格说明书.md`。
- 每份文档头部标注版本与更新日期。
- 图片统一放入所属目录的 `images/` 子目录；论文图片统一放 `07-论文/images/`，正文用相对路径引用。
- 文档更新同样走 Git 提交（`docs:` 类型）。

### 3.4 文档与代码的一致性

设计先行、实现对照设计；设计发生变更时，同步更新对应文档，避免"文档与实现脱节"。论文素材直接复用设计与实验数据，保证前后一致。

## 四、附录：常用命令速查

```bash
# 查看状态 / 差异
git status
git diff

# 功能开发
git switch dev
git switch -c feature/ga-paper dev
git add <files>
git commit -m "feat(组卷): 实现适应度函数"
git push -u origin feature/ga-paper

# 合并回 dev（保留分支历史）
git switch dev
git merge --no-ff feature/ga-paper

# 阶段发布
git switch main
git merge --no-ff dev
git tag -a v0.5-组卷算法 -m "组卷算法完成"
git push origin main --tags

# 撤销 / 临时保存
git restore <file>            # 撤销工作区改动
git stash / git stash pop     # 临时保存
```
